## Problem Statement

CTRL(외부 source-of-truth 시스템)에서 매장 관제시간(`controlTimes`)이 변경되면 IoT 서버의 `monitoring_schedules`가 자동/수동으로 동기화되어야 한다. 현재는 IoT 서버 관리자가 수동으로 매장별 요일별 시간을 입력해야 하고, CTRL과 어긋나면 알림 시각 판정(`is_in_schedule`)이 잘못된다.

두 진입점:
1. **자동**: CTRL → n8n → 우리 webhook endpoint (실시간)
2. **수동**: `stores/[store_id]` 페이지 "외부 서버에서 동기화" 버튼 (관제자가 필요할 때 강제 동기화)

## Demand Evidence

- 사용자가 직접 CTRL 명세 문서 작성·공유 (`shared/20260526_ctrl_server_integration.md` 418줄) — 통합 요구가 구체적·실재
- n8n 워크플로우 이미 설치·기본 설정 완료 — 사용자가 인프라에 시간 들임 = 진짜 필요
- `backend/app/services/external_poll.py` + `POST /stores/{id}/schedules/sync` 라우터가 이미 존재 — 같은 문제를 1차 단방향 polling으로 풀어둔 흔적
- Phase 1 plan에서 T5(CTRL 양방향) "이번 제외" 결정 — 그 시점엔 협의 미숙, 이번 명세 문서가 그 협의의 결과

## Status Quo

- IoT 서버에 매장 등록 후 관제자(admin)가 `/stores/[store_id]` 화면에서 요일별 관제시간을 손으로 입력
- 매장 운영시간 변경 시 CTRL에서 수정 + IoT에서도 수동 수정 (양쪽 따로) → 누락·불일치 빈번
- `external_poll.py`의 base_url + `/api/schedules/{store_id}` 호출 패턴은 가상의 외부 서버 가정 — CTRL의 실제 endpoint(`/api/store/store_detail?storeNo=`)와 매핑 안 맞음
- `POST /stores/{id}/schedules/sync` 라우터는 살아있지만 외부 호출이 실패할 가능성 큼

## Target User & Narrowest Wedge

**User**: 무인매장 관제자 (admin1~5) + 매장 운영 담당자

**Narrowest wedge**: 매장 1개의 `stores/[store_id]` 화면에서 "외부 서버에서 동기화" 버튼 1회 클릭 → CTRL의 현재 controlTimes를 monitoring_schedules에 정확히 반영. 이것만으로도 운영 가치 발생(매장 시간 변경 발생 시 즉시 자동 갱신).

Webhook은 자동화 다음 단계 — 운영자가 "버튼만 있어도 되겠다"가 아니라 "전 매장 일제히 자동 갱신"을 원함을 사용자가 표현했으므로 함께 묶음.

## Constraints

- **Scope = A안 controlTimes 한정**. 매장명·주소·담당자·연락처·장비 IP/비밀번호 5필드는 IoT DB에 저장 X. 보안 책임 구간을 좁힘.
- **DB 스키마 변경 0**: 기존 `monitoring_schedules` 테이블 재사용. alembic 추가 마이그레이션 없음.
- **`is_manual=1` 행 보존**: 관제자가 임시로 손댄 매장은 자동 동기화로 덮어쓰지 않는다.
- **보안 키 평문 노출 금지**: `X-SERVER-API-KEY`, `CTRL_WEBHOOK_SECRET`은 `.env`에만, 로그·에러 메시지·git 절대 X.

## Premises (확정)

1. **CTRL이 controlTimes의 source-of-truth.** IoT는 미러링만, IoT에서 controlTimes 변경 가능하되 `is_manual=1` 마킹 — 그 행은 CTRL 동기화에서 보존.
2. **n8n → IoT webhook 인증**: `X-WEBHOOK-SECRET` 헤더 + `.env`의 `CTRL_WEBHOOK_SECRET` 검증. 불일치 시 401. n8n 워크플로우에서 헤더 등록.
3. **eventType 처리**: `created` / `updated` / `time_updated` → controlTimes 추출 후 monitoring_schedules 반영. `deleted` → 로그만 남기고 수동 처리 대기 (운영 실수 보호).
4. **stores row 미존재 매장 webhook**: 무시 + 로그. Edge가 `POST /api/v1/edge/register`로 매장을 먼저 등록한 다음 CTRL이 자동으로 보내는 webhook에서 schedules 채워짐.
5. **UI 동기화 버튼**: 기존 `POST /stores/{id}/schedules/sync` 라우터 재사용. 단 `services/external_poll.py`의 URL·payload 매핑을 CTRL 실제 스펙(`/api/store/store_detail`, `controlTimes` 배열)에 맞게 재구성. 결과는 `acknowledged_count`/`updated_count` 식 응답으로 명시.

## Approaches Considered

### Approach A: 신규 service + webhook router (recommended)

**Summary**: `services/ctrl_sync.py` 신규(CTRL 스펙 전담) + `routers/webhooks.py` 신규(n8n 수신). 기존 `external_poll.py`는 deprecate 처리 후 제거.

```
[Backend 코드 변경]
backend/app/services/ctrl_sync.py      신규 — CTRL API client + controlTimes 매핑
backend/app/routers/webhooks.py        신규 — POST /webhooks/ctrl/store
backend/app/routers/schedules.py       변경 — sync 라우터가 ctrl_sync 호출
backend/app/services/external_poll.py  삭제 또는 deprecated 주석
backend/app/config.py                  변경 — CTRL_API_BASE, CTRL_API_KEY, CTRL_WEBHOOK_SECRET 추가
backend/.env.example                   변경 — 세 키 placeholder 추가

[Frontend 코드 변경]
frontend/app/stores/[store_id]/page.tsx   변경 — "외부 서버에서 동기화" 버튼 + 결과 표시
frontend/lib/api.ts                       변경 — syncSchedules({storeId}) 호출
```

| 항목 | 값 |
|---|---|
| Effort | M (human ~4h / CC ~30min) |
| Risk | Low — 기존 schedules 라우터/모델 재사용, DB 스키마 변경 0 |
| Pros | 명확한 모듈 경계 / external_poll의 가상 endpoint 잔재 제거 / 테스트 격리 쉬움 |
| Cons | 코드 라인 증가 / external_poll → ctrl_sync rename의 git history 단절 |
| Reuses | `monitoring_schedules` model / `POST /stores/{id}/schedules/sync` 라우터 / `is_manual` 정책 |

### Approach B: external_poll.py 그대로 수정 (rename 없음)

**Summary**: `external_poll.py` 안의 URL/payload만 CTRL 스펙으로 갱신, webhook router만 신규.

| 항목 | 값 |
|---|---|
| Effort | S (human ~2h / CC ~15min) |
| Risk | Low |
| Pros | git diff 최소 / 파일 rename 안 함 |
| Cons | 이름이 의미와 어긋남(`external_poll` ≠ webhook receiver) / 향후 다른 외부 시스템 추가 시 더 꼬임 |

### Approach C: 풀스택 미러링 (D1에서 reject된 C안)

**Summary**: 매장명·주소·담당자 + 장비 IP/비밀번호 5필드까지 IoT DB 미러링.

| 항목 | 값 |
|---|---|
| Effort | L (human ~3일 / CC ~3h) |
| Risk | High — 비밀번호 5필드 보안 책임, AES 키 회전 절차, 추가 컬럼/테이블 |
| Pros | 한 화면에서 모든 매장 데이터 통합 운영 |
| Cons | 보안 표면 ↑ / CTRL이 이미 source-of-truth인데 이중 저장 / 키 회전 시 동시 배포 어려움 |
| **Reject 사유** | D1에서 명시 거절 — 보안 책임 구간 좁힘 우선 |

## Recommended Approach

**Approach A**. 이유:

- `external_poll`이라는 이름이 미래의 다른 외부 시스템(예: 결제·재고 등)을 시사하는데 실제로는 CTRL 전용 → `ctrl_sync`로 책임 분리가 정확
- 신규 webhook router를 별도 파일에 두면 다른 webhook(예: 향후 결제 webhook)이 같은 컨벤션으로 들어올 자리 확보
- 테스트가 `tests/test_ctrl_sync.py` 단일 파일로 깔끔 (Phase 1의 test_alerts 사례처럼 한 도메인 한 테스트 파일)

## Open Questions

1. **n8n 워크플로우 등록 절차** — IoT 서버의 webhook URL(예: `https://pcbang-iot-api.multion.synology.me/api/v1/webhooks/ctrl/store`)을 누가 n8n에 등록? (사용자가 직접 vs orchestrator가 가이드 후 운영팀)
2. **`time_updated` vs `updated` 차이 처리** — 명세상 둘 다 매장 데이터 변경이지만 `time_updated`는 controlTimes만 변경. 우리는 controlTimes만 추출하니 두 eventType을 동일 처리해도 무방. 그러나 로깅에는 구분 유지 권장.
3. **CTRL 401 또는 timeout 발생 시 UI 메시지** — "외부 서버 연결 실패. CTRL 운영팀에 문의" 같은 문구. 사용자 결정 필요.
4. **신규 매장 created webhook을 받았으나 우리 stores에 없는 케이스의 빈도** — 정상 운영에서는 Edge 등록 → CTRL 등록 → 동기화 순서를 기대. 만약 CTRL이 먼저 등록되는 흐름이면 매장이 "잠긴" 상태로 남음. 운영 관찰 후 결정.

## Success Criteria

- **자동(webhook)**:
  - n8n에서 `https://.../webhooks/ctrl/store`로 POST → 5초 이내 200 OK 응답
  - 매장이 우리 DB에 있으면 `monitoring_schedules` row 7개(요일별)가 controlTimes에 맞춰 갱신 (`is_manual=1` 행 제외)
  - 매장이 없으면 200 OK + 로그에 `store_not_found store_no=N` 기록
  - `X-WEBHOOK-SECRET` 헤더 불일치 또는 누락 시 401
- **수동(UI 버튼)**:
  - 클릭 → 백엔드가 CTRL `/api/store/store_detail?storeNo=N` 호출 (`X-SERVER-API-KEY`) → controlTimes 추출 → DB 반영
  - 응답: `{ success: true, data: { updated_count: N, skipped_manual: M } }`
  - 화면에 "X일 동기화 완료, Y건 수동 설정 보존" 토스트
  - CTRL 401/timeout/매장 미존재 시 명확한 에러 메시지

## Distribution Plan

- 신규 artifact 없음 (기존 backend·frontend 컨테이너 재배포)
- `.env`에 3개 신규 키 추가 (`CTRL_API_BASE`, `CTRL_API_KEY`, `CTRL_WEBHOOK_SECRET`) — 운영 서버 `.env` 갱신 필요
- 운영 단계: backend systemd restart → frontend rebuild + pm2 restart → n8n에서 우리 URL 등록 → 매장 1곳에서 "외부 동기화" 버튼 테스트 → CTRL에서 그 매장 controlTimes 변경 → webhook 자동 갱신 확인

## The Assignment

**한 가지 실제 행동**: 사용자가 n8n 워크플로우에 IoT 서버의 webhook URL을 등록할 위치를 미리 정해 둔다.
- 예: `Webhook` 노드 → URL `https://pcbang-iot-api.multion.synology.me/api/v1/webhooks/ctrl/store`
- 헤더 `X-WEBHOOK-SECRET: <random>` 추가
- 한 매장의 controlTimes를 CTRL에서 변경해서 n8n 워크플로우가 실제로 트리거되는지 dry-run

이걸 미리 해두면 backend 구현 완료 즉시 5분 안에 end-to-end 검증 가능.

## What I noticed about how you think

- **명세 문서를 사용자가 직접 가져옴** — `shared/20260526_ctrl_server_integration.md` 418줄을 본인이 쓰거나 받아오면서 보안 주의 섹션·암호화 예시 3종(Java/Node/Python)을 다 챙김. "외부 시스템 연동은 명세부터"라는 본능이 자연스럽게 깔려있다.
- **보안 키 평문 노출에 대한 의식** — 명세 문서 §⚠️ 보안 주의를 명시적으로 적어둔 점. 키 회전·폐기 절차까지 정리. 이건 사고 한 번 겪은 사람의 글버릇이거나 그런 팀의 영향을 받은 흔적.
- **scope를 좁히는 결정** — D1에서 A안(controlTimes만)을 선택. "전부 다 미러링하자" 유혹을 거절하고 "CTRL이 source-of-truth면 우리는 미러링만"으로 책임을 분리. T5를 Phase 1에서 제외한 것과 일관된 사고.
- **운영자 관점** — "외부 서버에서 동기화" 버튼을 명시함. webhook 자동화만으로 충분할 텐데 굳이 수동 버튼을 둠. 자동 동기화를 못 믿어서가 아니라 운영자가 "지금 당장 강제로 맞추고 싶다"는 순간을 떠올린 것. UX에 운영 흔적이 묻어남.

## plan-eng-review 락인 결정사항

원본 design doc의 5 premises는 office-hours에서 이미 합의. 본 review에서 추가 락인:

- **A1 (architecture)**: CTRL `daySn` (1=일, 2=월, ..., 7=토) ↔ `monitoring_schedules.day_of_week` (0=월, ..., 6=일, Python `weekday()` 표준)은 모델 line 14 + alert.py:30에서 확인됨. `services/ctrl_sync.py` 의 private helper `_ctrl_daysn_to_our_dow(n) = (n + 5) % 7` 로 단일화. `tests/test_ctrl_sync.py` 에 7개 요일 전체 테이블 단위테스트(daySn=1→6, 2→0, 3→1, 4→2, 5→3, 6→4, 7→5) 필수.
- **C1 (code quality)**: `services/external_poll.py` 는 **DEPRECATED 주석** 추가 후 코드 보존. `routers/schedules.py:sync_schedules` 의 import·호출은 `ctrl_sync.sync_store_schedules(store_id, db)` 로 교체. dead code는 명시적 deprecation marker로 표시.

### 2026-05-26 정책 정정 — is_manual 보존 폐기

라이브 검증 후 사용자 의도가 우리 기존 가정과 달랐음:

- **기존 (premise 1)**: "`is_manual=1` 행은 자동 동기화 시 보존" — `external_poll.py` 잔재
- **수정**: CTRL = source-of-truth. **is_manual 값과 무관하게 모든 controlTimes 갱신**. is_manual 컬럼은 그대로 유지(운영자 흔적 — 누가 손댔는지 추적용)
- 이유: 사용자가 운영자 화면에서 "스케줄에 따름 + 모든 요일 활성" 으로 설정해도 시간 자체가 안 바뀌는 게 혼란. 운영 정신 모델은 "CTRL 시간이 정답, 우리는 그걸 반영"
- 적용: `services/ctrl_sync.py:apply_control_times` 가드 제거. `tests/test_ctrl_sync.py` test 이름·assertion 반전 (`test_apply_overrides_is_manual_one`). 응답 형식은 `skipped_manual` 키 유지하되 값은 항상 0.

### Failure modes

| 코드패스 | 한 가지 현실 실패 | 테스트 | 에러 핸들링 | 사용자에게 보이는 메시지 |
|---|---|---|---|---|
| `_ctrl_daysn_to_our_dow` 오매핑 | 사용자가 의식 못 함 | 7요일 단위테스트 | N/A — 순수함수 | (silent) — 테스트로만 방어 |
| `fetch_store_detail` CTRL 401 | API 키 만료 | unit + e2e | httpx HTTPStatusError → 502 응답 | UI "외부 인증 실패. 운영팀 확인 필요" |
| `fetch_store_detail` timeout | CTRL 일시 장애 | unit (mock) | httpx.TimeoutException → 504 응답 | UI "외부 서버 응답 없음. 잠시 후 재시도" |
| `apply_control_times` is_manual=1 덮어쓰기 시도 | 운영자 수동 설정 침범 (REGRESSION) | unit | WHERE is_manual=0 가드 | (방어됨) |
| webhook secret 불일치 | n8n 설정 어긋남 | unit | 401 + log | (n8n 운영자 확인) |
| 같은 webhook 2회 수신 | n8n 재시도 또는 운영 손동작 | unit | controlTimes 덮어쓰기 → 자연 idempotent | (silent OK) |
| `deleted` webhook 받음 | CTRL에서 매장 폐점 | unit | log만, DB 변경 X | 운영자가 직접 결정 (실수 보호) |

**Critical gap**: 없음. `_ctrl_daysn_to_our_dow`의 silent 매핑 오류는 단위테스트로 방어가 필수 — 그래서 A1 결정에 명시.
