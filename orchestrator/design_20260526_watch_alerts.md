## Problem Statement

무인매장 운영 중 의심스러운 알림(예: 비정상적 냉장고 접근, 시간외 출입 패턴, 의심 행동)을 발견했을 때, 관제자가 단순 ack 처리로 흘려보내지 않고 **"특별관리"** 항목으로 분리하여 메모를 남기고 상태(확인중/처리완료)를 추적할 수 있어야 함.

기존 ack 흐름은 binary(미확인 → 확인됨)인 반면, 관심로그는 상태 머신(확인중 → 처리완료) + 메모 + 등록자/처리자 추적이 필요한 별도 워크플로우.

## What Makes This Cool

- 관제자가 "이상한데 정확히 뭔지는 모르겠다" 싶을 때, 일단 등록 후 사후 조사 가능
- 알림 폭주 시에도 진짜 의심스러운 것만 골라 별도 추적
- 사후 감사: 누가 언제 무엇을 의심했고, 어떻게 처리됐는지 기록 남김 → 무인매장 분쟁/사고 대응에 핵심

## Constraints

- 기존 `alert_events` 스키마 무변경 (ack/snapshot/importance 메커니즘 그대로 재사용)
- 인증: 기존 `get_current_user` 세션 인증 그대로
- 진입점: AlertList의 AlertRow, VideoPopup — 큰 UI 재작업 없이 버튼 1개 추가
- 백엔드: PostgreSQL + Alembic, FastAPI async
- 프론트: Next.js 16 App Router, 다크 테마 (DESIGN.md 토큰)

## Premises (Lock-in)

1. **별도 테이블 `watch_alerts`** — D2 A 채택
   - `alert_event_id` FK로 원본 alert 참조
   - status enum: `pending`(확인중) / `resolved`(처리완료)
   - 메모는 등록 시 필수, 이후 수정 가능

2. **자동 ack 정책** — D1 A 채택
   - 관심로그 등록 = 원본 alert 자동 acknowledge
   - WS broadcast로 다른 관제자 메인에서 즉시 사라짐
   - 메인의 깨끗함 우선 ("확인처리 하는게 아니"는 워딩과 살짝 다르지만, 사용자 명시 선택)

3. **삭제는 hard delete** — soft delete 없음. `watch_alerts` row만 사라지고, 원본 `alert_events`는 보존.

4. **상태 전이는 양방향 허용** — pending → resolved 가 정상 흐름이지만, resolved → pending 되돌리기도 가능 (실수 복구). UI에서 confirm dialog로 보호.

5. **권한** — 모든 인증 사용자가 등록/조회/상태변경/삭제 동일하게 가능 (기존 ack 정책과 동일). 향후 role 분기 가능성은 열어둠.

## Approaches Considered

### Approach A: 별도 `watch_alerts` 테이블 + 자동 ack ✅ 선택

- 새 테이블, 새 라우터, 새 페이지
- `alert_events` 스키마 무변경
- 등록 시 단일 트랜잭션으로 watch insert + alert ack

### Approach B: `alert_events`에 `watch_*` 컬럼 추가

- 새 테이블 없이 컬럼만 추가 (`watch_status`, `watch_note`, `watched_by`, `watched_at`)
- 단순하지만 응집도 낮음, 삭제 시 원본 alert까지 위협, 확장 시 마이그레이션 폭탄
- → **탈락**

## Recommended Approach (Approach A 상세 설계)

### DB 스키마

```sql
CREATE TABLE watch_alerts (
    id              SERIAL PRIMARY KEY,
    alert_event_id  INTEGER NOT NULL REFERENCES alert_events(id) ON DELETE CASCADE,
    note            TEXT    NOT NULL,
    status          TEXT    NOT NULL DEFAULT 'pending'
                    CHECK (status IN ('pending', 'resolved')),
    created_by      INTEGER NOT NULL REFERENCES users(id),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    resolved_by     INTEGER REFERENCES users(id),
    resolved_at     TIMESTAMPTZ
);

CREATE INDEX idx_watch_alerts_status     ON watch_alerts(status, created_at DESC);
CREATE INDEX idx_watch_alerts_alert_event ON watch_alerts(alert_event_id);
```

- `ON DELETE CASCADE`: 원본 alert 삭제 시 watch도 함께 사라짐 (실무상 alert는 거의 안 지우므로 무해)
- `status` CHECK: DB 레벨 enum 강제 (Pydantic `Literal['pending', 'resolved']` 와 이중 보호)

### API 설계 (`/api/v1/watch-alerts`)

| Method | Path                       | Body / Query                      | 동작                                                                |
| ------ | -------------------------- | --------------------------------- | ------------------------------------------------------------------- |
| POST   | `/watch-alerts`            | `{alert_id: int, note: str}`      | watch insert + 원본 alert ack (단일 트랜잭션) + WS broadcast        |
| GET    | `/watch-alerts`            | `?status=pending\|resolved\|all`  | 필터 + alert 스냅샷 join, `created_at DESC`                         |
| PATCH  | `/watch-alerts/{id}`       | `{status?: str, note?: str}`      | 상태 전이 시 resolved_at/resolved_by 자동 채움 (또는 NULL로 되돌림) |
| DELETE | `/watch-alerts/{id}`       | -                                 | hard delete                                                         |

응답 스키마(GET/POST 공통):
```json
{
  "watch_id": 12,
  "status": "pending",
  "note": "냉장고 문 3분 이상 열려있음, CCTV 다시 보기 필요",
  "created_by": {"id": 1, "username": "admin1"},
  "created_at": "2026-05-26T22:14:33Z",
  "resolved_by": null,
  "resolved_at": null,
  "alert": {
    "alert_id": 4521,
    "store_id": 30263,
    "type_name": "냉장고 도어",
    "custom_name": "주류 냉장고 #2",
    "snapshot_url": "https://...",
    "stream_url": "https://...",
    "occurred_at": "2026-05-26T22:13:50Z",
    "importance": 4
  }
}
```

### WebSocket

- POST /watch-alerts 시 기존 `alert.acknowledged` broadcast 발생 → 다른 관제자 메인에서 자동 제거
- 신규 `watch.created` 이벤트는 **v1 생략**. /watch-logs 페이지는 진입/탭 전환 시 fresh fetch.
  - 향후 실시간 갱신 필요해지면 추가.

### Frontend

#### 신규 라우트: `/watch-logs`

```
┌─ 헤더(관심로그 탭 활성) ────────────────────────────────┐
│ [확인중] [처리완료] [전체]   총 12건       ↻ 새로고침   │
├──────────────────────────────────────────────────────┤
│ ┌─ Row ──────────────────────────────────────────┐  │
│ │ [snapshot 80x60]  매장 #30263 · 주류 냉장고 #2   │  │
│ │                   2026-05-26 22:13:50 발생       │  │
│ │                   "냉장고 3분 이상 열림, CCTV ..." │  │
│ │                   등록: admin1 · 22:14:33        │  │
│ │                   [확인중 배지]                   │  │
│ │                          [처리완료로] [✎ 메모] [🗑] │  │
│ └────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

- URL: `?status=pending` (default) / `?status=resolved` / `?status=all`
- 필터 토글은 useSearchParams + Suspense (기존 패턴, app/page.tsx 참조)
- 처리완료 row는 dim (opacity 0.7) + 처리시각 표시
- 삭제 / pending↔resolved 토글은 confirm dialog

#### 진입점 추가: AlertList의 AlertRow + VideoPopup

각 알림 행/팝업에 `★ 관심처리` 버튼 추가 → 모달:

```
┌─ 관심로그 등록 ─────────────────────────┐
│ 매장: #30263 · 주류 냉장고 #2 · 22:13:50 │
│                                          │
│ 메모 (필수)                              │
│ ┌────────────────────────────────────┐ │
│ │ [textarea, 4 lines, ≤ 500자]       │ │
│ └────────────────────────────────────┘ │
│                                          │
│           [취소]  [등록 + 확인처리]      │
└──────────────────────────────────────────┘
```

- 등록 후: 토스트 "관심로그에 등록되었습니다" + 메인에서 alert 자동 사라짐 (ack broadcast)
- 빈 메모는 disabled, 500자 제한

#### 헤더 네비

기존 헤더에 `관심로그` 탭 추가. 미처리 건수 배지(`pending` count)는 v1 생략 가능, 추후 WS로 가능.

## What I noticed about how you think

- "확인처리 하는게 아니 특별관리항목으로 빼서, 처리를 하는거야" — 사용자는 ack와 watch의 의미론적 차이를 명확히 구분하고 있음. 그래서 D1에서 "자동 ack"를 선택하면서도 메인에서 사라지는 게 ack의 본래 의미와 다르다는 점은 의식했을 것. 만약 운영해보고 어색하면 ack 안 함 모드로 전환 가능 (premise 1 변경).
- "삭제 도 만들어서 해당 내용을 삭제할 수 있도록 하자" — soft delete 같은 복잡한 것 없이 단순 hard delete를 선호. 운영 도구다운 직설적 선택.
- 필터 3개 (확인중/처리완료/전체) 같은 명확한 enumeration — 상태가 더 늘어나는 걸 원하지 않음. v1 단순함 유지가 핵심.
